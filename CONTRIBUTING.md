# Вклад в Limb

## Сообщить об ошибке

Создайте [issue](https://github.com/RSafargalin/Limb/issues). Укажите версию или SHA Limb,
версию Swift и ОС. Для протокольной ошибки укажите клиент и ревизию MCP, если они известны.
Приложите минимальный пример, шаги воспроизведения, ожидаемое и фактическое поведение.
Замените токены и приватные данные в примерах безопасными значениями.

## Предложить изменение

1. Для новой возможности сначала опишите сценарий использования в issue.
2. Сделайте fork репозитория и создайте рабочую ветку от `develop` исходного репозитория.
3. Запустите `./scripts/ci.sh`. Если меняется поведение для пользователя, проверьте
   соответствующий сценарий и обновите публичный пример или описание API.
4. Откройте pull request в `develop`. Опишите изменение, как его проверить и повлияет ли оно
   на существующий код Swift или взаимодействие с MCP-клиентом.

Для заголовков PR и коммитов используйте
[Conventional Commits](https://www.conventionalcommits.org/en/v1.0.0/).
Примеры заголовков — `fix(stdio): handle EOF consistently` и
`docs: update the server example`.

## Локальные проверки

Используйте macOS 26 или новее и Swift 6.2 или новее. Для отдельного теста можно
запустить `swift test --filter <имя>`. Набор в `Tests/` покрывает в том числе
макросы, современный и прежние режимы MCP и обмен по stdio.

| Команда | Проверка |
| --- | --- |
| `./scripts/ci.sh` | Сборка и тесты текущих файлов рабочей копии, включая отдельные проверки исчерпания файловых дескрипторов. |
| `./scripts/ci.sh pr <git-ref>` | Те же проверки из снимка указанного локального Git-коммита. |
| `./scripts/ci.sh release <git-ref>` | Тесты из снимка коммита в release-конфигурации с обоими JSON-кодеками и отдельные проверки исчерпания файловых дескрипторов. |
| `./scripts/inspector-ci.sh [<git-ref>]` | Внешняя проверка stdio через MCP Inspector на каждой ревизии и с обоими кодеками. Без аргументов проверяет рабочую копию. |
| `./scripts/inspector-ci.sh --release <git-ref> <report.json>` | Полная проверка Inspector на точном коммите, включая длительную нагрузку и отчёт JSON. |

Для каждого прогона используется активный Swift. Чтобы проверить другую установленную
версию Xcode, задайте `DEVELOPER_DIR` при запуске. Команды печатают результаты в терминал.

Для прогона Inspector нужны Node.js и npm. Inspector 2.16.0 поддерживает ветки
Node.js 22 начиная с 22.23.4, ветку 24 начиная с 24.22.1 и версии от 26.12.1.
Команда устанавливает зависимости из lockfile во временный каталог. Она проверяет
согласование ревизии, вызовы инструментов, чтение ресурсов и шаблонов, получение
промптов и варианты автодополнения. На одном соединении проверяет, что после ошибки
аргументов сохраняется состояние и можно продолжить работу. Inspector также проверяет
две последовательные формы ввода, включая отказ, отмену и запись результата после
принятия обеих форм. Закреплённый MCP-клиент на TypeScript проверяет прогресс запроса
и получение отмены обработчиком Limb. Короткие нагрузочные сценарии проверяют
конкурентные вызовы и доставку уведомлений подписчику.
При первом запуске нужны доступные реестры зависимостей.

Перед слиянием PR запускайте проверку Inspector, если он меняет ядро MCP, обработку
запросов, транспорт stdio, кодеки или поведение публичного API при обмене с клиентом.
Кандидат и финальная версия проходят проверку с `--release` на коммите будущего тега.

Релизный профиль даёт каждой комбинации ревизии и кодека 30 секунд смешанной
нагрузки. Inspector планирует 250 запросов в секунду в режиме `--load-open-loop`
и допускает до 16 запросов в полёте. Если генератор просыпается с задержкой,
запросы остаются в расписании. Половина нагрузки приходится на вызовы инструментов,
четверть на чтение ресурсов и четверть на получение промптов. Для успеха должны
стартовать минимум 99% запланированных запросов, все запущенные запросы должны
пройти без ошибок.
Суммарное время подачи нагрузки по матрице составляет четыре минуты.

```sh
./scripts/inspector-ci.sh --release <sha> .limb-private/reports/inspector-<sha>.json
```

Отчёт содержит SHA, версии инструментов, параметры нагрузки, результаты проверок
по именам и доступные счётчики запросов по каждой комбинации. Скрипт сверяет
матрицу со списком ревизий, которые поддерживает собранный Limb. При сбое команда
возвращает ненулевой код. Отчёт различает проваленные (`failed`), прерванные
(`interrupted`) и незапущенные (`not_run`) комбинации. Путь к отчёту должен быть новым.
При публикации выпуска прикладывайте прошедший отчёт с SHA тега к GitHub Release.
Диагностический вывод остаётся в терминале.

Публичная документация описывает использование Limb и наблюдаемое поведение.
Внутренние планы, ADR, отчёты о тестировании и замеры хранятся отдельно.
