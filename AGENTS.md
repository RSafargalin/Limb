# Правила работы с Limb

## Коммиты и заголовки PR

Используйте Conventional Commits 1.0.0. Заголовок PR должен соответствовать тому же формату. Для рабочей ветки он становится заголовком squash-коммита.

```text
<type>[optional scope][!]: <description>

[optional body]

[optional footer(s)]
```

- `type` обязателен. Используйте `feat` для новой возможности и `fix` для исправления ошибки. Для других изменений подходят `docs`, `test`, `ci`, `build`, `refactor`, `perf`, `style`, `chore` и `revert`.
- `scope` необязателен. Если он помогает понять область изменения, заключите его в круглые скобки. Примеры областей Limb — `stdio`, `server`, `json`, `macros` и `testing`.
- В Limb пишите тип и область строчными буквами, а после двоеточия и пробела добавляйте короткое описание изменения на английском. Описывайте результат конкретным глаголом.
- Тело коммита необязательно. Отделите его пустой строкой и используйте, чтобы объяснить причину изменения или уточнить поведение.
- Если нужны завершающие поля, отделите их пустой строкой от тела или заголовка. Форматы полей — `Token: value` и `Token #value`. Используйте дефисы внутри имени поля, например `Reviewed-by`. Значение может занимать несколько строк и заканчивается перед следующим полем.
- Стандарт позволяет отмечать несовместимость через `!` перед двоеточием, через поле `BREAKING CHANGE: <description>` или обоими способами. В Limb используйте оба и указывайте, как мигрировать. Стандарт также распознаёт `BREAKING-CHANGE` как эквивалент, а в Limb для записи используйте `BREAKING CHANGE:`.

```text
fix(stdio): handle EOF consistently
docs: update the server example
ci: run the SwiftPM tests locally
```

При переименовании публичного параметра укажите в завершающем поле, чем заменить старое имя.

```text
feat(server)!: rename the shutdown grace option

BREAKING CHANGE: Use shutdownGrace in place of shutdownGraceSeconds.
```

Справочник по стандарту доступен в [Conventional Commits 1.0.0](https://www.conventionalcommits.org/en/v1.0.0/).

## GitHub Project и задачи

Используйте [GitHub Project Limb](https://github.com/users/RSafargalin/projects/1), привязанный к [RSafargalin/Limb](https://github.com/RSafargalin/Limb). Issue в репозитории служит карточкой публичной работы. Project отображает её состояние и место в плане. Связанный PR содержит реализацию и описание проверки.

- `Board` показывает работу по статусам `Backlog` → `Ready` → `In progress` → `In review` → `Done`.
- `Backlog` содержит очередь задач. В `Ready` перемещайте задачи с понятным результатом, способом проверки и учтёнными зависимостями. Обычно достаточно одной основной задачи в работе.
- `Releases` группирует задачи по полю `Milestone`. Используйте имя целевой версии для вехи, например `0.0.1`. Описывайте цель выпуска в вехе, а области работы отмечайте метками вроде `stdio`, `http` и `macros`.
- `P0` означает блокер ближайшего выпуска, `P1` — существенную задачу текущей итерации, `P2` — работу, которую можно отложить.
- Для каждой issue запишите, кого затрагивает изменение, ожидаемый результат и критерий готовности. Для бага добавьте минимальное воспроизведение, фактическое поведение и применимые версии Limb, Swift, ОС и MCP. Большие задачи делите на части, которые можно проверить отдельно.
- Держите одну активную веху. При регулярном разборе очереди уточняйте приоритеты, зависимости и состав ближайшего выпуска.

Публичные карточки и PR описывают наблюдаемое поведение, интерфейсы и проверяемые результаты. Автоматические тесты и их фикстуры храните в `Tests/`. Проектные черновики, ADR, сравнительные замеры и отчёты о тестировании храните локально в `.limb-private/`. Перед коммитом проверьте список файлов в индексе.

## Ветки Git Flow

| Ветка | Назначение и путь слияния |
| --- | --- |
| `main` | Ветка по умолчанию и линия выпусков. Принимает проверенные релизы и срочные исправления. |
| `develop` | Интеграционная ветка. Принимает обычные задачи и служит основой следующего выпуска. |
| Короткоживущие рабочие ветки | Создаются от `develop` и вливаются обратно через PR и squash merge. |
| `release/X.Y.Z` | Создаётся от `develop`, когда в нём собран согласованный объём выпуска. Служит для стабилизации, проверки кандидатов и подготовки документации выпуска. Вливается в `main` и обратно в `develop` с сохранением истории. |
| `hotfix/X.Y.Z` | Создаётся от тега текущего выпуска для срочного исправления. Обычно вливается в `main` и `develop`. Если уже открыта релизная ветка, включите исправление и в готовящийся выпуск. |

Для интеграции `release/*` и `hotfix/*` используйте merge commit. Это сохраняет общий предок и историю исправлений при обратном слиянии. Оформляйте сообщение такого коммита по Conventional Commits, например `chore(release): merge 0.0.1`.

## PR и проверки

1. Держите PR небольшим и привязанным к одному связному результату. Укажите, что изменилось, как это проверено и затронуты ли публичный Swift API или поведение MCP. Сведения о миграции перенесите в сообщение squash-коммита.
2. Для PR в `develop` укажите ссылку на issue и закройте её после слияния, когда выполнен критерий готовности. GitHub применяет автоматическое закрытие по `Fixes #123` к PR в ветку по умолчанию. Используйте его для PR в `main`, который полностью решает задачу.
3. Запустите `./scripts/ci.sh` для проверки рабочей копии. Для изменений кодека также запустите `swift test --traits FoundationJSON`.
4. Перед слиянием PR в `develop`, `release/*` или `main` запустите `./scripts/ci.sh pr <git-ref>` на коммите с проверяемым результатом пробного слияния. Повторите проверку при изменении PR или целевой ветки. Указывайте проверенный SHA и результат в PR. Локальная команда завершает работу с ненулевым кодом при ошибке.
5. На том же коммите запускайте `./scripts/inspector-ci.sh <git-ref>` при изменениях ядра MCP, обработки запросов, транспорта stdio или кодеков, а также при изменениях API, которые могут повлиять на обмен с MCP-клиентом.

## Независимое написание и проверка тестов

1. Тесты пишет отдельный агент **Sol**, который не участвовал в написании кода проверяемого изменения и не видел его реализацию. Запускайте его со свежим контекстом (`fork_turns: none`). Он работает по описанию задачи, критериям готовности и публичному контракту, включая необходимые сигнатуры API, и может читать тестовую инфраструктуру. Исходники реализации, diff и обсуждение реализации остаются вне его контекста.
2. После любой правки заново определяйте затронутую область и проверяйте её целиком. Проследите связанные вызовы, зависимости, переходы состояния, обработку ошибок и освобождение ресурсов, где это применимо. Сверяйте код, тесты и проектные решения с требованиями, документацией и применимой спецификацией. Одинаково критично оценивайте решения любого автора. Проверяйте, что тест воспроизводит условия дефекта и способен заметить нарушение контракта. Для гонок проверяйте значимые порядки событий, включая соседние пути завершения операции.
3. Код и тесты независимо ревьюят три других агента — **Sol**, **Terra** и **Luna**, которые их не писали. Для итогового ревью запускайте проверяющих со свежим контекстом (`fork_turns: none`). Передавайте всем один снимок изменений, критерии задачи, применимую документацию и спецификацию. Каждый самостоятельно проверяет всю затронутую область, запускает соответствующий набор на одном снимке и сообщает команду, результат и замечания. Прежние замечания и выводы других рецензентов обсуждайте после получения независимых оценок. Успешный прогон подтверждает сценарии, которые покрывают тесты. Готовность требует сверки покрытия с контрактом.
4. Исправьте обнаруженные проблемы и повторите ревью затронутой области и прогон на снимке, который собираетесь влить. После успешной проверки и прогона у всех трёх агентов вливайте PR рабочей ветки в `develop` через squash merge.

## Версии и релизы

- Используйте SemVer отдельно от формата коммитов. В серии `0.x` увеличивайте `PATCH` для совместимых исправлений, а `MINOR` — для заметных новых возможностей и намеренных несовместимых изменений. Указывайте несовместимость и способ миграции в release notes.
- Начиная с `1.0.0`, совместимые исправления увеличивают `PATCH`, совместимые возможности — `MINOR`, а несовместимые изменения публичного контракта — `MAJOR`.
- Один выпуск соответствует одной вехе с целевой версией. Теги содержат версию, например `0.0.1`. Для очередных кандидатов используйте `X.Y.Z-rc.N`. Исправленный кандидат получает новый тег.
- Тег кандидата ставьте на проверяемый коммит в `release/X.Y.Z`. Тег финальной версии ставьте после проверок на коммите слияния в `main`.
- При оценке совместимости учитывайте публичные Swift API, макросы и их сгенерированный код, traits пакета и наблюдаемое поведение MCP.
- Перед выпуском проверьте критерии вехи и запустите `./scripts/ci.sh release <sha>` на точном коммите выпуска с минимальной заявленной и актуальной версиями Swift. Команда запускает оптимизированные тесты с обоими JSON-кодеками.
- Перед тегированием кандидата и финальной версии запускайте `./scripts/inspector-ci.sh --release <sha> <report.json>` на коммите, который получит тег. Прогон проверяет каждую поддерживаемую ревизию MCP отдельно с каждым JSON-кодеком и запускает длительную нагрузку. Прикладывайте к GitHub Release прошедший JSON-отчёт с SHA тега. Храните сырые журналы и сравнительные замеры локально.
- В release notes перечисляйте пользовательские изменения, подтверждённую совместимость, известные ограничения и шаги миграции, если они нужны.

Справочник по версиям доступен в [SemVer 2.0.0](https://semver.org/spec/v2.0.0.html).
